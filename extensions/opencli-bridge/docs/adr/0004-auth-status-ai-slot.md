# Auth-status surfacing + adaptive AI-slot chain

Two problems: (1) the agent flies blind about login state, and (2) research plans hardcode an AI site that may be unreachable. Probing `opencli auth status` for per-site login **hangs** (it asks the browser bridge site-by-site, 60s+ before returning), so per-site login cannot be a live prompt signal. Instead the Bridge surfaces the cheap global signal — `opencli doctor` connectivity (daemon OK, browser bridge connected) — in the system prompt and status line; the agent uses it to prefer api-strategy sites when the browser bridge is down. Per-site login stays out of scope; `opencli auth status` remains available as a manual command. For the AI slot in research plans, the profile's AI site is no longer trusted blindly: the slot is filled by the first reachable adapter in the chain chatgpt → gemini → qwen → deepseek → grok → kimi (validated against the registry), with the profile's own AI site as the terminal fallback. `claude` remains reachable via the explicit `sites` parameter (and `qwen` is now in the chain). Rejected: blocking startup on `opencli auth status` (hangs startup), and trusting the profile's AI site unconditionally (silently produces error calls when the adapter is absent).
